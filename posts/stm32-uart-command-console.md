# 给STM32做一个串口命令控制台：帧协议、状态机与LED控制

> 源码：[github.com/NaHSIT/STM32ZET6Project/tree/main/projects/06-uart-command-console](https://github.com/NaHSIT/STM32ZET6Project/tree/main/projects/06-uart-command-console)

7月14日，按键和定时器已经能稳定协作，我开始给开发板加一条真正的数据通道：通过USART1接收电脑命令，控制两盏LED，再把最新状态主动回传。

我不想只做一个“收到什么就原样发回”的串口回显，于是给它设计了最小帧协议和接收状态机。做到这里，STM32第一次不只是按固定程序运行，而是能听懂外部发来的指令。

---

## 1. 硬件组成

- STM32F103ZET6。
- USART1：`PA9`发送，`PA10`接收。
- USB转TTL模块，双方共地。
- LED1：`PB5`；LED2：`PE5`。
- 四个板载按键和TIM2继续保留，串口通信时仍能响应本地操作。

串口参数设为9600波特率、8位数据、1位停止位、无校验。速度不高，但调试终端足够稳定，也方便用逻辑分析仪逐位观察。

---

## 2. 为什么要加帧头和帧尾

串口是一条连续字节流，没有天然的“这一条消息结束了”。我约定数据包格式为：

```text
@L1ON\r\n
```

`@`表示一帧开始，`\r\n`表示结束。有效命令包括`L1ON`、`L1OFF`、`L2ON`、`L2OFF`和两条翻转命令。

接收中断用三个状态推进：等待`@`、读取正文、等待`\n`。只有完整收到帧尾才设置`Serial_RxFlag`，主循环不会处理半截字符串。

---

## 3. 一个藏得很深的越界问题

最初缓冲区长度是256，接收索引却用了`uint8_t`。代码还写了`if (index >= 256)`，看起来有保护，实际上8位变量最大只有255，加一后直接回到0，这个条件永远不可能成立。

我把索引改为`uint16_t`，并在写入之前判断：

```c
if (index < SERIAL_RX_CAPACITY - 1U) {
    Serial_RxPacket[index++] = (char)byte;
} else {
    index = 0U;
    state = RX_WAIT_START;
}
```

这样永远给字符串结尾的`\0`留一个位置，超长帧直接丢弃，不会写出数组边界。

格式化输出也从`vsprintf`换成`vsnprintf`。前者不知道目标缓冲区有多大，一条长日志就可能破坏栈；后者会按容量截断。

---

## 4. 中断收包，主循环执行

中断只负责收字节和拼帧。收到完整命令后，主循环用`strcmp`匹配动作，执行完再清`Serial_RxFlag`。标志未清期间，中断不会开启下一帧，避免主循环还在读字符串时缓冲区被覆盖。

本地按键、定时闪烁和串口命令同时存在，但没有哪一项会等待数秒。LED状态变化后统一回报：

```text
LED1=1 LED2=0
```

这条状态反馈很重要。控制端不能只知道“命令发出去了”，还要知道设备最后处于什么状态。

---

## 5. 调试时遇到的乱码

第一版终端全是乱码，我先查代码，最后发现USB转TTL还停在115200，而程序配置的是9600。串口出问题时，我现在固定检查四件事：波特率、数据格式、交叉接线和共地。

还有一次只能发不能收，是把TX接到了TX。串口的命名站在各自设备角度，正确接法必须是TX对RX、RX对TX。

---

> 从这一篇开始，代码不只是控制硬件，还要面对不完整输入、超长数据和通信不同步。可靠通信的第一步不是把字节发出去，而是明确一帧从哪里开始、在哪里结束、出错时怎样恢复。
