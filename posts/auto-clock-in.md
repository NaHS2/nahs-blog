# 写了个自动晚点名打卡工具：从忘记打卡到全自动托管

大学生活中有很多让人头疼的琐事，晚点名打卡就是其中之一。每天晚上 21:00 左右，辅导员在群里喊一声"打卡啦"，你得放下手头的事，点开学校小程序，等它加载、授权、定位……有时候刷着视频就忘了，第二天名字出现在未打卡名单上，有苦说不出。

某个晚上我忽然想：与其每天定闹钟提醒自己，不如让程序替我完成这件事。

花了几天时间，从逆向学校小程序的接口逻辑开始，到最终在云服务器上架起一套全自动打卡系统。这篇文章不讲具体代码，只分享**从头到尾的技术思路和实现方法**。

---

## 1. 整体思路

这件事分两步走：

| 阶段 | 目标 | 核心工作 |
|------|------|----------|
| **逆向分析** | 搞清楚学校系统怎么运作的 | 反编译小程序、还原接口链路、破解签名与定位校验 |
| **搭建服务** | 让打卡自动执行 | CLI 工具 → 定时后端服务 → 云服务器部署 |

先跑通手动打卡，证明链路可行；再加定时调度，让它在后台自动运转。

---

## 2. 逆向：搞清楚学校系统怎么运作的

学校没有提供任何 API 文档，所有信息都得靠自己挖出来。

### 2.1 拿到小程序源码

学校打卡用的是微信小程序（uni-app 框架开发）。微信小程序的代码包在手机文件系统中以 `.wxapkg` 格式存在，拿到文件后用开源工具反编译，就能还原出完整源码。其中几个文件最为关键：

- `http/request.js` — 请求拦截器，**签名算法就在这里**
- `http/authUtil.js` — OAuth 认证核心逻辑
- `http/index.js` — 50 多个 API 接口的完整定义
- `pages/views/stusign.js` — 打卡页面的完整交互逻辑（定位、拍照、提交）
- `utils/index.js` — 工具函数（日期格式化、Haversine 距离计算）

> 反编译仅用于个人学习研究，了解系统交互逻辑。

### 2.2 抓出 wechatAppId

`wechatAppId` 是学校认证体系的一个重要参数，但它不在反编译后的源码里明文出现（和微信小程序的 AppID 不是同一个东西），而是藏在**运行时的网络请求中**。

我写了一段 JS 脚本，注入到学校打卡页面的控制台，做四层递进扫描：

**第一层·内存快照** — 遍历 `window` 全局对象树（最深 6 层），查找名为 `wechatAppId` 的属性。uni-app 项目有时会把这类配置挂在 Vue 实例或全局变量上。

**第二层·静态源码** — 遍历页面中所有 `<script>` 标签，用正则匹配包含 `wechatAppId` 的代码行。

**第三层·本地存储** — 遍历 `localStorage` 和 `sessionStorage`，查找键名匹配或值中包含特征字符串的条目。

**第四层·网络拦截** — 如果前三层都没命中，脚本会 hook 原生的 `fetch` 和 `XMLHttpRequest`，拦截之后所有的网络请求。一旦某个接口响应的 JSON 里出现了 `wechatAppId` 字段，立刻捕获输出。

四层扫描有一个核心锚点：**这个值一定以 `ocr` 开头**。这是一个非常强的特征——只要在运行环境里找到以 `ocr` 开头且字段名匹配 `wechatAppId` 的字符串，就一定是要找的目标。

实际操作流程很简单：通过学校 WebVPN 登录统一认证平台，跳转到打卡页面，F12 打开控制台，粘贴脚本执行。如果静态快照没命中，脚本会提示"后台监听已启动"，刷新一下页面（F5），页面重新加载时发起的网络请求就会被拦截到，`wechatAppId` 瞬间弹出。

### 2.3 梳理接口调用链 + 获取 OpenID

有了 `wechatAppId` 和反编译源码，下一步是把学校的接口调用链完整梳理出来。学校后端用的是**飞源（flySource）统一认证平台**，完整的认证和打卡链路如下：

> 微信登录获取 openid → OAuth 换取 access_token → 查任务列表 → 查任务详情（含宿舍坐标）→ 查当日打卡状态 → 提交打卡

这条链路里最关键的是 **openid**——学号和密码自己当然知道，但 openid 必须通过微信登录流程才能拿到。获取 openid 有两种方式：

- **手机抓包**：配置 HTTPS 代理（Proxyman 或 Charles），在学校小程序登录时抓取网络请求，响应体里直接包含 `openid` 字段
- **验证码登录**：学校系统同时支持验证码登录（`grant_type=captcha`），先请求验证码图片，识别后提交登录，返回的 `oauthId` 就是 openid。这种方式不需要抓包，但要多处理一步验证码识别

拿到 openid 后，学号 + 密码 + openid 三个凭据齐全，就能在学校系统里以你的身份完成任何操作了。

### 2.4 还原签名算法

这是整个逆向过程中最耗时的一步。学校的每个业务请求都带了一个 `FlySource-sign` 头，签名不对，服务器直接拒绝。

签名逻辑写在 `request.js` 的请求拦截器里。反编译后的变量名已被混淆成单个字母，但不影响理解逻辑。还原出来的计算规则：

1. 取当前毫秒级时间戳
2. 时间戳 + token 拼接，做一次 MD5
3. 取请求 URL 路径（去掉查询参数），尾部拼上 `?sign=`
4. 将第 3 步和第 2 步的结果拼接，再做一次 MD5
5. 最终格式：`<MD5>1.<Base64时间戳>`

验证方法很朴素：用同一组参数（相同的时间戳、token、URL 路径），分别跑 JS 原版和自己的实现，输出一致就说明还原正确。这一步花了我整整一个下午。

### 2.5 绕过 GPS 定位校验

学校打卡会校验 GPS 坐标是否在宿舍范围内。但查看任务详情接口的返回数据就会发现——它直接返回了**宿舍的精确经纬度、房间 ID，以及允许的定位精度上限**。

既然如此，策略就很简单了：以宿舍坐标为中心，每次提交时加一个随机小偏移（±0.0005 度，大约几十米），然后用 **Haversine 球面距离公式**计算实际偏移距离，确认在允许范围内再提交。每次打卡的坐标都略有不同，看起来就像正常 GPS 漂移。

有一个容易忽略的细节：距离计算必须用 Haversine 公式，不能用平面几何近似。学校源码 `utils/index.js` 里有完整实现，直接照着翻译即可，否则算出来的距离会对不上。

### 2.6 stuTaskId：容易被忽略的校验字段

提交打卡时，请求体里除了位置信息，还有一个 `stuTaskId` 字段。它不是服务器返回的，而是**客户端按固定规则自己生成的**。

阅读 `stusign.js` 里的提交逻辑可以发现生成方式：将六个字段（纬度、经度、定位精度、日期、任务 ID、文件 ID）按**特定顺序**拼成 JSON 字符串，然后对整个字符串做 MD5。

这里有一个坑：key 的顺序必须和 JS 源码中的对象字面量顺序完全一致，否则 MD5 结果不匹配。Python 3.7+ 的 dict 虽然保序，但你声明时就得以正确的顺序写。

## 3. 实现：从命令行到云端服务

逆向工作做完、链路验证通过之后，开始搭建自动化系统。

### 3.1 CLI 工具：先跑通再说

第一步没有直接上服务端，而是写了一个命令行交互工具。它做的事情很简单：

- 输入学号、密码、openid，登录学校系统
- 菜单选择：查记录、立即打卡、看任务列表
- 打卡时自动遍历所有活跃任务，逐一提交
- 支持按月份查询打卡历史

这个阶段的目标只有一个——**确认整条链路是通的**。能手动完成一次打卡之后，再考虑自动化。

### 3.2 后端服务：定时自动执行

命令行能用，但手动操作还是可能忘记。于是搭了一个常驻后端服务，核心需求非常简单：**每天 21:00，自动完成打卡**。

技术选型上用了 **FastAPI + APScheduler + PostgreSQL**。APScheduler 设置 cron 触发器，每天 21:00 触发一次批量打卡任务——遍历所有开启自动打卡的用户，并发执行。

为了避免所有用户同一秒请求学校服务器（既不合理也容易被检测异常），每个用户执行前会加一段**随机等待时间**，默认 0~5 分钟，用户可以在设置里自定义范围。这样请求会自然地分散在 21:00 之后的几分钟内。

### 3.3 凭据安全

服务器上存着同学的学号、密码、openid，安全不能马虎：

- **密码** — bcrypt 哈希存储（不可逆），同时存一份 MD5 哈希（学校登录接口要求传 MD5，这是协议限制）
- **OpenID** — AES-256-CBC 加密存储，密钥只存在于服务器环境变量，数据库泄露也无法解密
- **接口鉴权** — JWT Token，过期需重新登录
- **请求限流** — Nginx 层面限制认证接口频率，防止暴力破解

### 3.4 数据库设计

围绕"谁、什么时间、打了什么卡"这条主线，设计了五张表：

| 表 | 职责 |
|----|------|
| 用户表 | 账号、密码哈希、加密 openid、打卡开关、延迟与偏移参数 |
| 系统配置 | 全局键值对 |
| 任务缓存 | 缓存宿舍坐标等任务信息，减少对学校接口的重复请求 |
| 打卡记录 | 每次打卡的日期、坐标、距离、结果 |
| 操作日志 | 每一步执行详情，方便排查失败原因 |

### 3.5 部署上线

买了一台阿里云轻量服务器，部署链路如下：

> **Nginx**（反向代理 + 接口限流）→ **Supervisor**（守护 uvicorn 进程，崩溃自动重启）→ **FastAPI**（业务逻辑）→ **PostgreSQL**（数据存储）

写了一键部署脚本，自动完成装依赖、配数据库、建 `.env` 文件、配 Supervisor 守护、配 Nginx 反代的全部操作。更新更简单——一个脚本搞定 git pull + 重装依赖 + 重启服务。

## 4. 一些心得

**先跑通，再扩展。** 一开始命令行版本几十行代码就能完成一次打卡。确认链路通了之后，才逐步加上定时调度、数据库、部署脚本。不要一上来就设计大而全的系统——你不知道哪个环节会卡住你。

**逆向靠耐心和交叉验证。** 学校系统的签名算法没有文档、变量名被混淆、逻辑散落在多处。花了一整个下午逐行比对，才把签名逻辑完全还原。核心技巧：**同一组参数，分别跑原版和自己的实现，输出一致就是对的。**

**多层扫描的思路很有用。** wechatAppId 的获取就是一个例子——内存找不到就去源码找，源码找不到就去存储找，存储找不到就 hook 网络请求守株待兔。很多看起来难以获取的运行时参数，都可以用类似的递进策略拿到。

**合理使用，模拟真实行为。** 自动打卡是防止遗忘的保险机制，不是鼓励违规。设计上也刻意模拟了真实用户——随机延迟、GPS 小幅偏移、请求频率控制。既不给学校服务器造成压力，也是一种对服务提供方的尊重。
