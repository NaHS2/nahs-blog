# 某定位签到系统认证流程分析与安全研究

> 在线演示：[sfrog.online](https://sfrog.online)（测试账号 `test`，密码 `test0000`，可预览前端界面，无后端数据交互）

> ⚠️ **声明**：本文仅用于学习网络协议分析、接口认证机制和自动化测试技术，不建议将相关技术用于绕过学校、企业或其他组织的管理要求。读者在实际使用过程中应遵守相关法律法规以及目标系统的服务协议。

大学生活中有很多让人头疼的琐事，晚点名打卡就是其中之一。每天在固定时间要求学生在指定位置完成签到，这种基于地理位置和时间窗口的考勤机制在高校中十分普遍。出于对这套系统背后技术原理的好奇，我决定深入研究一下它的认证流程和安全机制。

花了几天时间，从分析学校小程序的接口逻辑开始，到最终理解整个认证链路的运作方式。这篇文章不讲具体代码，只分享**从头到尾的技术分析思路和安全考量**。

---

## 1. 系统架构概览

在深入分析之前，先梳理这套签到系统的整体架构。从客户端与服务端的交互关系来看，系统可以抽象为以下模型：

```
┌─────────────────────────────────────────────────┐
│  客户端（微信小程序）                              │
│  ┌──────────┐  ┌──────────┐  ┌───────────────┐  │
│  │ 签名生成  │  │ GPS 定位 │  │ 任务参数构造   │  │
│  └─────┬─────┘  └────┬─────┘  └───────┬───────┘  │
│        │              │                │          │
└────────┼──────────────┼────────────────┼──────────┘
         │    ⚠️ 信任点1 │    ⚠️ 信任点2  │ ⚠️ 信任点3
         │  签名由客户端 │  坐标由客户端  │  校验字段由
         │  自行计算     │  单方上报      │  客户端生成
         ▼              ▼                ▼
┌─────────────────────────────────────────────────┐
│  服务端                                           │
│  ┌──────────┐  ┌──────────┐  ┌───────────────┐  │
│  │ 签名校验  │  │ 坐标校验  │  │ 任务合法性校验  │  │
│  └──────────┘  └──────────┘  └───────────────┘  │
│                                                    │
│  ❌ 无设备绑定  ❌ 无行为分析  ❌ 无多源位置验证    │
└─────────────────────────────────────────────────┘
```

> ⚠️ 标记了三个关键信任点——这些环节完全依赖客户端上报的数据，是后续安全分析的核心关注点。

## 2. 协议分析

学校没有提供任何 API 文档，所有信息都需要从客户端入手分析。

### 2.1 小程序代码结构

学校打卡用的是微信小程序（uni-app 框架开发）。微信小程序的代码包在手机文件系统中以 `.wxapkg` 格式存在，获取文件后用开源工具反编译，就能还原出完整源码。其中几个文件最为关键：

- `http/request.js` — 请求拦截器，**签名逻辑所在**
- `http/authUtil.js` — OAuth 认证核心逻辑
- `http/index.js` — 50 多个 API 接口的完整定义
- `pages/views/stusign.js` — 打卡页面的完整交互逻辑（定位、拍照、提交）
- `utils/index.js` — 工具函数（日期格式化、球面距离计算）

> 反编译仅用于个人学习研究，了解系统交互逻辑。

### 2.2 关键认证参数的运行时定位

系统认证体系中有一个重要的标识参数（以下称为 `authId`），它不在反编译后的源码里明文出现（和微信小程序的 AppID 不是同一个东西），而是藏在**运行时的网络请求中**。

我通过浏览器控制台在页面运行时环境中递进扫描——从全局变量、页面源码、本地存储一路查到网络请求拦截——最终在客户端侧的通信数据中定位到了该参数。这里不展开具体脚本，核心思路是利用客户端调试工具追踪运行时数据流，这是理解系统认证链路的第一步。

### 2.3 认证链路分析

有了上述参数和反编译源码，下一步是把学校的接口调用链完整梳理出来。学校后端用的是**某第三方统一认证平台**，完整的认证链路如下：

> 微信登录获取用户标识 → OAuth 换取 access_token → 查任务列表 → 查任务详情（含目标坐标范围）→ 查当日签到状态 → 提交签到

这条链路里最关键的是**用户唯一标识符（openid）**——学号和密码自己当然知道，但 openid 必须通过微信登录流程才能拿到。

**注意：学校后端的 openid 获取接口实测已不可用**，通过后端请求获取 openid 这条路走不通，验证码登录等方式也已失效。openid 只能由用户**自行从客户端获取**，主要途径：

- **代理抓包**：配置 HTTPS 代理（Proxyman、Charles 或 Fiddler），在手机或模拟器上打开学校小程序/应用进行登录操作，抓取网络请求，从响应体中提取 `openid`。网页端同理，通过浏览器开发者工具的 Network 面板抓取即可。
- **控制台脚本**：认证标识参数可以通过浏览器控制台在签到页面运行时环境中捕获，思路与 2.2 节一致——利用客户端调试工具在本地拦截和扫描关键凭证。

**安全观察**：用户标识符的获取完全依赖客户端侧操作，服务端未对请求来源做额外的设备验证。这意味着一旦用户的核心凭据（学号、密码、openid）同时泄露，就能在任何设备上以该用户身份完成认证——这是后续风险评估的重要一点。

### 2.4 签名机制分析

这是整个分析过程中最耗时的一步。学校的每个业务请求都带了一个自定义签名头，签名不对，服务器直接拒绝。

签名逻辑写在 `request.js` 的请求拦截器里，反编译后的变量名已被混淆成单个字母。分析后发现：**该系统采用基于时间戳与会话令牌的双因素签名机制**，客户端将时间戳、令牌与请求路径组合后进行哈希计算，服务端侧独立计算并比对校验。

这里的关键发现是：签名所需的全部材料（令牌、算法、计算顺序）均存储于客户端代码中，反编译后即可完整还原。验证方式是在同一组参数下分别运行客户端原版和自己还原的实现，比对输出是否一致。

**安全观察**：当签名密钥和算法完全由客户端持有时，服务端实际上只能验证"请求是否来自一个知晓签名规则的人"，而无法验证"请求是否来自合法用户本人"。这个设计将安全边界建立在代码混淆之上，而非密码学保证。

### 2.5 定位校验机制分析

签到系统会校验提交的 GPS 坐标是否在目标范围内。分析任务详情接口的返回数据后发现：**服务端直接返回了目标坐标和允许精度上限**。

这揭示了系统的定位校验模型：

> 客户端上报坐标 → 服务端计算与目标坐标的距离 → 判断是否在允许范围内 → 返回结果

**安全观察**：这是一个典型的**客户端单点上报模型**。服务端独立验证链条中缺少以下环节：
- 未结合 IP 地理定位做交叉校验
- 未引入基站或 WiFi 指纹辅助定位
- 未对历史坐标变化轨迹做合理性分析

在缺少多源验证的情况下，定位校验的有效性完全取决于客户端上报数据的真实性。这个设计问题在物联网和 LBS（基于位置的服务）领域是一个被广泛讨论的安全课题。

### 2.6 请求体校验字段分析

提交签到请求时，请求体中包含一个**服务端未下发、由客户端自行生成的校验字段**。分析客户端代码后发现，该字段是将若干业务参数按固定顺序拼接后做哈希计算得到的。

**安全观察**：校验字段完全由客户端根据已知信息自行计算，服务端无法通过它来验证请求的合法性——任何掌握了生成规则的人都可以构造出合法请求。这反映了系统中一个更深层的架构问题：**服务端将部分安全校验能力委托给了客户端，而客户端代码是可以被逆向的**。

## 3. 可行性验证

分析工作完成后，需要通过可控的测试来验证发现的问题是否真实存在。这里强调：以下工作是在**封闭测试环境**中进行的，目的是确认安全分析的结论。

### 3.1 通信行为复现

首先进行了单次通信行为的复现验证。编写了一个命令行测试工具，能够完成认证链路的完整流程：登录鉴权 → 查询任务 → 提交签到数据。目标是确认**整条链路是否可以在标准 HTTP 客户端中完整复现**。

验证结果表明：服务端对请求来源没有设备指纹校验，任何能够提供合法凭据和正确签名参数的 HTTP 客户端都可以完成完整交互。这确认了 2.4 节中关于"签名机制未绑定设备身份"的判断。

### 3.2 时序行为验证

在确认单次链路可复现后，进一步验证了系统对**时序行为**的检测能力。搭建了一个测试调度环境（FastAPI + APScheduler + PostgreSQL），在固定时间窗口内以不同时间间隔和并发模式发送测试请求。

验证结果表明：当请求在时间上适度分散、内容格式符合正常范围时，服务端未表现出异常检测行为。这确认了 2.5 和 2.6 节中关于"服务端缺乏行为分析能力"的判断。

> 测试环境的所有请求均在可控范围内进行，未对生产系统造成负载压力。

### 3.3 凭据安全设计

在测试环境搭建过程中，需要考虑凭据管理的安全性（即使是测试数据）：

- **密码** — bcrypt 哈希存储（不可逆），同时存一份 MD5 哈希（目标系统登录接口要求 MD5 格式，这是协议限制）
- **用户标识符（OpenID）** — AES-256-CBC 加密存储，密钥只存在于服务器环境变量，数据库泄露也无法解密
- **接口鉴权** — JWT Token，过期需重新登录
- **请求限流** — Nginx 层面限制认证接口频率，防止暴力破解

### 3.4 测试数据管理

围绕"谁、什么时间、提交了什么数据"这条主线，测试数据分五类存储：

| 数据集 | 用途 |
|----|------|
| 用户表 | 账号、密码哈希、加密 openid、测试开关、时延参数 |
| 系统配置 | 全局键值对 |
| 任务缓存 | 缓存目标坐标等任务信息，减少对目标接口的重复请求 |
| 操作记录 | 每次操作的日期、坐标、距离、结果 |
| 操作日志 | 每一步执行详情，方便分析异常原因 |

### 3.5 测试环境部署

测试环境部署在一台阿里云轻量服务器上：

> **Nginx**（反向代理 + 接口限流）→ **Supervisor**（守护 uvicorn 进程，崩溃自动重启）→ **FastAPI**（测试调度逻辑）→ **PostgreSQL**（测试数据存储）

## 4. 安全风险分析

基于以上协议分析和可行性验证，从架构层面总结以下风险发现。

### 4.1 架构级风险评估

这套系统的安全设计中存在一个根因：**信任边界划分不合理**。

| 信任点 | 问题 | 根因 |
|--------|------|------|
| 签名生成 | 密钥与算法存于客户端，可逆向还原 | 将认证能力委托给不可信环境 |
| 位置数据 | 完全信任客户端单方上报，无多源校验 | 缺乏服务端侧的独立验证链路 |
| 校验字段 | 客户端自行生成，服务端无法鉴别真伪 | 安全校验逻辑放置在不可信端 |
| 设备身份 | 无设备指纹绑定，凭据可在任意设备使用 | 缺乏设备-账号-会话的强绑定 |
| 行为检测 | 无明显异常行为监控 | 缺乏用户行为基线建模 |

这些问题的共同点是：**系统将客户端视为可信执行环境，而客户端代码是可以被逆向分析的**。在零信任模型下，客户端不应承担安全关键计算（如签名生成、数据校验），这些能力应由服务端独立持有。

### 4.2 防护建议

针对以上风险，从工程角度提出以下改进方向：

**① 服务端侧签名**
将签名生成从客户端移至服务端。一种可行的方案是：客户端在认证成功后向服务端请求临时签名令牌（绑定当前会话和设备），后续业务请求携带此令牌，服务端独立校验。令牌可设置短有效期和一次性使用策略，即使被截获也无法重放。

**② 设备指纹绑定**
在认证阶段采集设备多维特征（硬件信息、操作系统版本、网络特征等），生成设备指纹并与用户账号绑定。当新设备登录时触发二次验证，异常设备直接拒绝。这会显著增加凭据泄露后的利用难度。

**③ 多源位置验证**
不只依赖客户端单次上报的经纬度，可结合：
- IP 地理定位做粗粒度校验
- 基站定位和 WiFi 指纹做辅助验证
- 历史坐标轨迹做合理性分析（是否从合理方向移动过来、速度是否合理）
- 任务详情接口不返回目标坐标和精度阈值

**④ 行为基线建模**
建立用户正常行为基线（签到时间分布、设备信息、网络环境、坐标变化模式），对偏离基线的操作触发人工审核或二次验证。即使攻击者掌握了所有凭据，也难以完全模拟正常用户的长期行为模式。

**⑤ 客户端代码加固**
对关键逻辑进行代码混淆和完整性校验，定期轮换签名密钥，提高逆向分析门槛。虽然客户端代码无法做到绝对安全，但显著增加分析成本本身就是有效的威慑。

**⑥ 接口层防御**
- 认证接口：严格频率限制 + 递增延迟 + 验证码
- 业务接口：IP 信誉检查 + 请求来源一致性校验
- 全局：异常流量检测 + 自动化攻击特征识别

## 5. 零信任架构对比

如果将这套系统重构为零信任模型，架构对比如下：

| 维度 | 当前设计 | 零信任改进 |
|------|----------|------------|
| 签名位置 | 客户端计算 | 服务端签发临时令牌 |
| 位置验证 | 单源（客户端 GPS） | 多源交叉验证（GPS + IP + 基站 + 轨迹） |
| 设备身份 | 无绑定 | 设备指纹 + 异常设备二次验证 |
| 行为监控 | 无 | 行为基线建模 + 异常检测告警 |
| 信任模型 | 隐式信任客户端 | 显式验证每一个请求 |
| 密钥管理 | 客户端硬编码 | 服务端动态下发，定期轮换 |

**核心理念**：零信任不预设任何一方可信。每一个请求都需要独立验证——无论它来自"看起来正常"的客户端还是一段脚本，服务端对它们的校验标准应当相同。

## 6. 一些心得

**先理解架构，再评估风险。** 一开始只是好奇系统的运作方式，但随着分析深入，才发现很多看似严密的设计背后存在系统性的信任边界问题。先完整梳理链路，再逐一标记信任点——你会发现架构图中的"信任边界"往往就是"风险边界"。

**逆向靠耐心和交叉验证。** 签名机制没有文档、变量名被混淆、逻辑散落在多处。花了一整个下午逐行比对，才把签名逻辑完全还原。核心技巧不变：**同一组参数，分别跑原版和自己的实现，输出一致才是对的。**

**多层扫描的思路很有用。** 关键认证参数的定位就是一个例子——内存找不到就去源码找，源码找不到就去存储找，存储找不到就 hook 网络请求守株待兔。这种递进策略不仅适用于逆向分析，在任何需要定位隐蔽信息的场景都有价值。

**安全分析的最终目的是推动改进，而非利用漏洞。** 分析这套系统的过程中，我越来越深刻地理解到：发现问题只是第一步，从架构层面理解问题的成因、并提出可落地的改进方案，才是完整的安全分析闭环。希望这篇文章的分析框架能为同类系统——无论是高校考勤、企业打卡还是物联网设备管理——的安全设计提供参考。
