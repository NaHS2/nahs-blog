# 某定位签到系统认证流程分析与安全研究

> 在线演示：[sfrog.online](https://sfrog.online)（测试账号 `test`，密码 `test0000`，可预览前端界面，无后端数据交互）

> ⚠️ **声明**：本文仅用于学习网络协议分析、接口认证机制和自动化测试技术，不建议将相关技术用于绕过学校、企业或其他组织的管理要求。读者在实际使用过程中应遵守相关法律法规以及目标系统的服务协议。

大学生活中有很多让人头疼的琐事，晚点名打卡就是其中之一。每天在固定时间要求学生在指定位置完成签到，这种基于地理位置和时间窗口的考勤机制在高校中十分普遍。出于对这套系统背后技术原理的好奇，我决定深入研究一下它的认证流程和安全机制。

花了几天时间，从分析学校小程序的接口逻辑开始，到最终理解整个认证链路的运作方式。这篇文章不讲具体代码，只分享**从头到尾的技术分析思路和安全考量**。

---

## 1. 整体思路

这件事分两步走：

| 阶段 | 目标 | 核心工作 |
|------|------|----------|
| **逆向分析** | 理解系统的认证与校验机制 | 反编译小程序、还原接口链路、分析签名与定位校验 |
| **安全评估** | 验证发现的安全风险并提出防护建议 | 概念验证 → 风险评估 → 防护建议 |

先理清系统的运作逻辑，再基于发现的问题提出改进方向。

---

## 2. 逆向：理解系统的认证与校验机制

学校没有提供任何 API 文档，所有信息都需要从客户端入手分析。

### 2.1 小程序代码结构分析

学校打卡用的是微信小程序（uni-app 框架开发）。微信小程序的代码包在手机文件系统中以 `.wxapkg` 格式存在，获取文件后用开源工具反编译，就能还原出完整源码。其中几个文件最为关键：

- `http/request.js` — 请求拦截器，**签名算法就在这里**
- `http/authUtil.js` — OAuth 认证核心逻辑
- `http/index.js` — 50 多个 API 接口的完整定义
- `pages/views/stusign.js` — 打卡页面的完整交互逻辑（定位、拍照、提交）
- `utils/index.js` — 工具函数（日期格式化、Haversine 距离计算）

> 反编译仅用于个人学习研究，了解系统交互逻辑。

### 2.2 关键参数的运行时定位

`wechatAppId` 是学校认证体系的一个重要参数，但它不在反编译后的源码里明文出现（和微信小程序的 AppID 不是同一个东西），而是藏在**运行时的网络请求中**。

我写了一段 JS 脚本，注入到学校打卡页面的控制台，思路很简单：在页面运行时环境中递进扫描，从全局变量、页面源码、本地存储一路查到网络请求拦截，最终捕获到目标参数。具体脚本不在此展开，核心思路是利用浏览器控制台在客户端运行时环境中定位关键凭证。

### 2.3 认证链路分析 + OpenID 获取方式

有了 `wechatAppId` 和反编译源码，下一步是把学校的接口调用链完整梳理出来。学校后端用的是**某第三方统一认证平台**，完整的认证和打卡链路如下：

> 微信登录获取 openid → OAuth 换取 access_token → 查任务列表 → 查任务详情（含宿舍坐标）→ 查当日打卡状态 → 提交打卡

这条链路里最关键的是 **openid**——学号和密码自己当然知道，但 openid 必须通过微信登录流程才能拿到。

**注意：学校后端的 openid 获取接口实测已无法使用**，通过后端请求获取 openid 这条路根本走不通，验证码登录等方式也已失效。openid 只能由用户**自行从客户端获取**，主要途径：

- **代理抓包**：配置 HTTPS 代理（Proxyman、Charles 或 Fiddler），在手机或模拟器上打开学校小程序/应用进行登录操作，抓取网络请求，从响应体中提取 `openid`。网页端同理，通过浏览器开发者工具的 Network 面板抓取即可。
- **控制台脚本**：`wechatAppId` 是认证体系中的另一个关键参数，可以通过浏览器控制台在打卡页面运行时环境中捕获，思路与 2.2 节一致——利用客户端调试工具在本地拦截和扫描关键凭证。

从安全角度看，openid 的获取完全依赖客户端侧操作，服务端并未对请求来源做额外的设备验证——这意味着一旦用户的学号、密码和 openid 同时泄露，就可以在任何设备上以该用户身份完成认证。

### 2.4 签名算法还原

这是整个分析过程中最耗时的一步。学校的每个业务请求都带了一个 `FlySource-sign` 头，签名不对，服务器直接拒绝。

签名逻辑写在 `request.js` 的请求拦截器里。反编译后的变量名已被混淆成单个字母，但不影响理解逻辑。还原出来的计算规则：

1. 取当前毫秒级时间戳
2. 时间戳 + token 拼接，做一次 MD5
3. 取请求 URL 路径（去掉查询参数），尾部拼上 `?sign=`
4. 将第 3 步和第 2 步的结果拼接，再做一次 MD5
5. 最终格式：`<MD5>1.<Base64时间戳>`

验证方法很朴素：用同一组参数（相同的时间戳、token、URL 路径），分别跑 JS 原版和自己的实现，输出一致就说明还原正确。这一步花了我整整一个下午。

### 2.5 GPS 定位校验机制分析

学校打卡会校验 GPS 坐标是否在宿舍范围内。但查看任务详情接口的返回数据就会发现——它直接返回了**宿舍的精确经纬度、房间 ID，以及允许的定位精度上限**。

这意味着定位校验完全依赖客户端上报的数据，服务端并未独立验证用户的实际位置。从安全评估的角度，以宿舍坐标为中心、每次提交时加一个随机小偏移（±0.0005 度，大约几十米），然后用 **Haversine 球面距离公式**计算实际偏移距离，确认在允许范围内即可通过校验。每次的坐标都略有不同，看起来就像正常 GPS 漂移，服务端无法区分真实定位和模拟数据。

有一个技术细节：距离计算必须用 Haversine 公式，不能用平面几何近似。学校源码 `utils/index.js` 里有完整实现，直接照着翻译即可，否则算出来的距离会对不上。

### 2.6 stuTaskId：客户端自生成的校验字段

提交打卡时，请求体里除了位置信息，还有一个 `stuTaskId` 字段。它不是服务器返回的，而是**客户端按固定规则自己生成的**。

阅读 `stusign.js` 里的提交逻辑可以发现生成方式：将六个字段（纬度、经度、定位精度、日期、任务 ID、文件 ID）按**特定顺序**拼成 JSON 字符串，然后对整个字符串做 MD5。

这里有一个细节：key 的顺序必须和 JS 源码中的对象字面量顺序完全一致，否则 MD5 结果不匹配。Python 3.7+ 的 dict 虽然保序，但声明时就得以正确的顺序写。

从安全角度看，这个字段完全由客户端根据已知信息自行计算，服务端无法通过它来验证请求的合法性——任何掌握了生成规则的人都可以伪造。

## 3. 验证：从概念验证到安全评估

分析工作做完、链路理解透彻之后，需要通过实际验证来确认发现的问题是否真实存在。

### 3.1 概念验证

第一步没有直接上服务端，而是写了一个命令行交互工具。它做的事情很简单：

- 输入学号、密码、openid，完成认证
- 菜单选择：查记录、提交签到、看任务列表
- 签到操作遍历所有活跃任务，逐一提交
- 支持按月份查询历史

这个阶段的目标只有一个——**确认整条链路可以在任意客户端完全模拟**。能手动完成一次完整流程之后，系统的安全边界就清晰了。

### 3.2 自动化验证

命令行能跑通，但为了评估批量自动化操作的可行性，搭了一个常驻后端服务来验证：**能否以无人值守的方式定时触发完整签到流程**。

技术选型上用了 **FastAPI + APScheduler + PostgreSQL**。APScheduler 设置 cron 触发器，每天固定时间触发一次批量任务——遍历所有测试账号，并发执行。

为了模拟真实用户行为（同时验证服务端是否有异常检测机制），每个账号执行前会加一段**随机等待时间**，默认 0~5 分钟。请求会自然地分散在几分钟内，但如果服务端缺乏行为分析能力，这种简单的时间分散就足以规避基础的频率限制。

### 3.3 凭据安全考量

如果真要存储用户凭据，安全不能马虎。这里的设计思路是：

- **密码** — bcrypt 哈希存储（不可逆），同时存一份 MD5 哈希（学校登录接口要求传 MD5，这是协议限制）
- **OpenID** — AES-256-CBC 加密存储，密钥只存在于服务器环境变量，数据库泄露也无法解密
- **接口鉴权** — JWT Token，过期需重新登录
- **请求限流** — Nginx 层面限制认证接口频率，防止暴力破解

### 3.4 数据库设计

围绕"谁、什么时间、提交了什么数据"这条主线，设计了五张表：

| 表 | 职责 |
|----|------|
| 用户表 | 账号、密码哈希、加密 openid、签到开关、延迟与偏移参数 |
| 系统配置 | 全局键值对 |
| 任务缓存 | 缓存宿舍坐标等任务信息，减少对学校接口的重复请求 |
| 操作记录 | 每次操作的日期、坐标、距离、结果 |
| 操作日志 | 每一步执行详情，方便排查失败原因 |

### 3.5 部署架构

买了一台阿里云轻量服务器，部署链路如下：

> **Nginx**（反向代理 + 接口限流）→ **Supervisor**（守护 uvicorn 进程，崩溃自动重启）→ **FastAPI**（业务逻辑）→ **PostgreSQL**（数据存储）

写了一键部署脚本，自动完成装依赖、配数据库、建 `.env` 文件、配 Supervisor 守护、配 Nginx 反代的全部操作。

## 4. 安全风险与防护建议

通过以上分析，该系统存在以下安全隐患：

### 4.1 风险总结

- **客户端信任过度**：定位数据、stuTaskId 等关键校验字段完全由客户端生成，服务端不做独立验证。
- **签名密钥硬编码**：签名算法和 token 存储在客户端代码中，反编译即可完整还原。服务端仅依赖一个静态签名头来验证请求合法性，无法防御重放攻击。
- **缺乏设备绑定**：OpenID 获取后即可在任意设备上完成认证，服务端未对请求来源做设备指纹校验。
- **定位数据可伪造**：服务端完全信任客户端上报的经纬度，且任务详情接口直接返回了目标坐标和允许精度——相当于公开了校验阈值。
- **行为分析缺失**：只要请求频率控制在合理范围、坐标在允许误差内，服务端无法区分正常用户和自动化脚本。

### 4.2 防护建议

针对以上风险，系统设计时可考虑以下改进措施：

- **设备可信校验**：引入设备指纹机制，绑定用户常用设备，异常设备登录需二次验证。即使凭证泄露，攻击者也无法在新设备上直接操作。
- **动态签名机制**：签名密钥不应硬编码在客户端。可考虑基于时间窗口的动态密钥（如 TOTP），或由服务端在认证阶段下发临时签名令牌，过期失效。
- **服务端位置验证**：结合 IP 地理定位、基站定位、WiFi 指纹等多源数据交叉校验，而非仅依赖客户端单次上报的经纬度。同时，任务详情接口不应返回目标坐标和允许精度阈值。
- **异常行为检测**：监控操作时间分布、坐标变化模式、请求频率、设备信息等指标，对偏离正常行为模式的账号触发人工审核或二次验证。
- **请求频率限制**：对认证接口和签到接口实施严格的频率限制和递增延迟，增加自动化批量操作的难度和成本。
- **客户端代码加固**：对关键逻辑进行代码混淆和完整性校验，定期轮换签名密钥，提高逆向分析门槛（虽然无法完全杜绝，但能显著增加攻击成本）。

## 5. 一些心得

**先理解，再验证。** 一开始命令行版本几十行代码就能完成一次完整流程。确认链路通了之后，才逐步深入分析每个环节的安全设计。不要一上来就试图完整复现整个系统——你不知道哪个环节的设计会出乎意料。

**逆向靠耐心和交叉验证。** 学校系统的签名算法没有文档、变量名被混淆、逻辑散落在多处。花了一整个下午逐行比对，才把签名逻辑完全还原。核心技巧：**同一组参数，分别跑原版和自己的实现，输出一致就是对的。**

**多层扫描的思路很有用。** wechatAppId 的获取就是一个例子——内存找不到就去源码找，源码找不到就去存储找，存储找不到就 hook 网络请求守株待兔。很多看起来难以获取的运行时参数，都可以用类似的递进策略定位。

**安全研究的价值在于发现问题、推动改进。** 分析这套系统的初衷是好奇心——想知道它是怎么运作的。但越深入越发现，很多看似严密的校验机制其实存在明显的薄弱环节。希望这篇文章的分析能为同类系统的安全设计提供参考，而不是鼓励绕过管理规则。
