# 用 C 语言手写哈夫曼编码：从堆排序到文件压缩

> 源码：[github.com/NaHSIT/Huffman-coding](https://github.com/NaHSIT/Huffman-coding)

大二学数据结构的时候，哈夫曼编码是我印象最深的一章。贪心策略、最小堆、二叉树遍历、前缀码——几乎把课程重点全串起来了。课本上的伪代码读懂了，但心里总觉得不踏实：真的懂了吗？

于是花了五月下旬的课余时间，用纯 C 语言从零实现了一套完整的哈夫曼文本压缩系统。不依赖任何第三方库，只靠标准库。写完之后回头看，踩的坑和学到的东西远比做十道课后题多。

---

## 1. 系统能做什么

整个程序以命令行菜单驱动，七个选项：

- 手动输入文本，当场压缩并显示密码本和 0/1 流
- 读取外部 `.txt` 或 `.c` 文件，读完自动编码
- 解压还原原始文本
- 查看、切分、清空历史编码日志

总共 500 行代码，拆成 11 个源文件，每个只做一个模块：核心算法、文件读取、日志写入、日志读取、日志切分。写完回头看看，这个划分方式让每个文件的逻辑都短到一眼能看完。

## 2. 算法分步拆解

### 2.1 字频统计

第一步很简单：遍历输入文本的每一个字节，用它的 ASCII 值直接当数组下标，累加计数。同时把首次出现的字符记进一个去重列表，后面只对出现过的字符建树。

但这里藏了一个当时让我 debug 到半夜的坑：`char` 在绝大多数 C 编译器下是**有符号的**，范围是 -128 到 127。中文等多字节字符的某个字节可能 ≥ 0x80，被解释为负数后直接做数组下标，行为是未定义的，程序直接崩溃。修复只需要一行：把每个字符强制转为 `unsigned char`，范围变为 0 到 255，数组访问就安全了。一个小小的类型转换，花了我两个小时。

### 2.2 构建最小堆

有了字频，接下来要为每个（字符，频率）对建堆。这里有一个常见误区：有人会把节点一个一个插入空堆，每个插入都是 O(log m)。更高效的做法是**先全部扔进数组，然后原地建堆**——从最后一个非叶子节点（位置 `(size-2)/2`）开始向前做下沉调整。一次 O(m) 就能建好。

下沉操作本身不复杂：比较当前节点和左右两个孩子，如果当前不是最小的，就和更小的孩子交换位置，然后递归向下继续调整，直到满足堆性质或到达叶子。

### 2.3 贪心构建哈夫曼树

这一步是哈夫曼编码的灵魂。每次从最小堆弹出两个频率最低的节点，作为左、右子树。创建一个新的内部节点，频率设为两者之和，左右指针挂上刚刚弹出的两个节点，再把新节点塞回堆里。

循环往复，直到堆里只剩一个节点——它就是哈夫曼树的根。

整个过程的本质是贪心：每次合并当前最小的两个，确保频率高的字符离根近（编码短）、频率低的字符离根远（编码长）。最终加权路径长度最小。

### 2.4 DFS 生成编码表

从根开始深度优先遍历，约定向左走记 0，向右走记 1。到达叶子节点时，整条路径上的 0/1 序列就是该字符的哈夫曼编码。

编码存入一个全局二维数组，以字符 ASCII 值为行索引。后续压缩时查表就是 O(1)。这里产出的编码天然满足**前缀码**性质：没有任何一个编码是另一个编码的前缀。这意味着解码完全不需要分隔符，走到一个叶子就必然完成了一个字符的解码。

### 2.5 压缩

有了编码表，压缩就是一趟遍历：逐个取原始文本的字符，查表拿到对应的 0/1 串，拼接到输出缓冲区。O(n) 完成。

### 2.6 解压

从头遍历刚才生成的 0/1 流，遇到 0 走左子树、遇到 1 走右子树。走到叶子就取出该字符追加到输出，指针弹回根节点，继续处理下一段。同样 O(n)。唯一的条件是必须持有压缩时那棵哈夫曼树。

## 3. 工程上的考量

算法本身不算复杂，但把一段能运行的伪代码变成一个可靠的命令行程序，中间补了不少工程细节。

**动态内存扩容。** 外部文件大小未知，所以设计了一个翻倍扩容策略：起始分配 1KB，读满后 `realloc` 把容量翻倍。翻倍策略的摊销时间复杂度是 O(1)，不会频繁触发重分配。读取完成后压缩缓冲区和解压缓冲区也同步按需扩容。

**日志系统。** 每次压缩操作自动以追加模式写入日志文件，记录原始文本、压缩后的 0/1 流、密码本对照表。提供查看、清空、以及按批次标记自动切分成独立文件的小工具。日志切分功能在多次压缩后能把一个庞大的日志拆成 `coding_log.txt.data_0`、`coding_log.txt.data_1`……，方便按需查阅某一次操作。

**错误处理。** 所有 `malloc` / `realloc` 返回值都检查了 NULL，所有 `fopen` 都检查了文件打开失败，解压前校验压缩标记防止未压缩就解压，`scanf` 返回值也做了合法性判断并清理输入缓冲区。对于一个 500 行的学生项目来说，这些处理比算法本身更花时间，但也是工程素养真正长进的地方。

## 4. 不足与反思

写完之后，回头看这套代码，坦率地说还有不少可以改进的地方。

**最大的问题：输出是文本 0/1 而不是二进制。** "压缩"完一看——文件比原文还大。因为每个 bit 占了一个字节的存储。下一版计划做真正的二进制位打包写入。

**哈夫曼树没有持久化。** 当前解压依赖"上次跑完还在内存里的哈夫曼树"，如果程序重启、或者编码和解码不在同一进程，解压就失败了。规范化哈夫曼编码（Canonical Huffman）可以解决这个问题——只存每个字符的码长，接收端按规则重建编码表。

**多字节字符编码可以更聪明。** 当前以单个字节为单位进行统计和编码，对中文来说，以 UTF-8 码点或常用词的粒度处理，压缩率会更高。
