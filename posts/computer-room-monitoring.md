# 从零搭建分布式机房监控系统：STM32 + ESP32 + OneNET + 全平台应用

机房里的设备不怕用，就怕环境出问题——温度高了服务器降频，湿度大了主板腐蚀，漏水更是灾难性的。市面上的动环监控系统动不动就是五位数的报价，对于学生实验室和创业团队的微型机房来说实在不划算。

于是我给自己定了一个目标：用最便宜的物料，从零搭一套能用的分布式机房监控系统。

整个过程全部一个人搞定——原理图自己画、PCB 自己 layout 投板、元件自己焊、外壳打孔自己装、固件自己调、服务器自己配、网页和 App 自己写。几个月下来完整跑通了物联网开发的整个链路，回头看，每个环节学到的东西都比课堂深刻得多。

---

## 1. 整体架构：一主一从 + 一个眼睛

物理上需要监控的地点不止一个——机房本身、配电柜角落、空调出风口……如果每个位置都接网线，布线成本比硬件还高。所以我采用了一种轻量级的分布式方案：**用两个 STM32 做主从串口互联，再加一个带摄像头的 ESP32 做视觉节点**。

```
┌─────────────────────────────────────────────────┐
│                 OneNET 云平台                     │
│            (MQTT 数据中转 + 物模型)                │
└──────┬────────────┬──────────────┬──────────────┘
       │ MQTT       │ MQTT         │ HTTP API
  ┌────┴────┐  ┌────┴─────┐  ┌───┴──────────┐
  │ STM32主机│  │ ESP32-S3 │  │ PC 网页 + App │
  │ 数据汇聚 │  │ AI 视觉  │  │ 监控 + 控制   │
  └────┬────┘  └──────────┘  └──────────────┘
       │ USART 一线通
  ┌────┴────┐
  │ STM32从机│
  │ 传感器   │
  └─────────┘
```

四层角色各有分工：

| 层级 | 核心硬件 | 做什么 |
|------|----------|--------|
| 采集层 | STM32F103C8T6 从机 | 挂载全部传感器和执行器，运行本地自动保护逻辑 |
| 汇聚层 | STM32F103C8T6 主机 + ESP8266 | 接收从机数据、OLED 展示、WiFi 连网、MQTT 上下行 |
| 视觉层 | ESP32-S3 + OV2640 + ST7789 LCD | 定时抓拍上传自建 YOLO 服务器，检测机房人数 |
| 应用层 | PC 网页 + Android App | 实时仪表盘、趋势图表、远程开关控制、报警管理 |

从机部署在机房深处，和一堆传感器绑在一起；主机放在靠近门口有 WiFi 信号的位置，再加一根三芯线连到从机的串口。这样每个分布式点位只需要两个 STM32 加一个 ESP8266，不需要拉网线。

---

## 2. 从机：它能独立活下来

从机是整个系统里最"硬核"的部分。从画原理图到投板焊接，再到上电调试——它不依赖网络、不依赖主机、不依赖云端，哪怕三者全断，它依然能保护机房。

### 2.1 传感器阵容

从机挂了六类传感器，覆盖机房环境的关键维度：

- **DHT11** 温湿度 — 数字协议，三根线解决
- **MQ2** 烟雾 — 模拟量输出，经过 ADC 采集后按校准公式换算 ppm
- **HW038** 水位 — 接触式传感器，百分比换算
- **光敏电阻** — 检测机房照明是否正常
- **ADC 多通道** — 为扩展传感器预留

传感器数据每两秒刷新一轮，主循环按固定节奏采集、判断、显示、上报，不搞复杂的中断嵌套。

### 2.2 执行器和自动保护

传感器只是眼睛，执行器才是拳头。从机接了五种输出设备：

- **排风扇**（继电器）— 温度或烟雾超标时强制通风
- **电磁阀**（继电器）— 水位过高时自动打开排水
- **LED1 报警灯** — 烟雾浓度分级提示
- **LED2 补光灯** — 环境过暗自动补光
- **蜂鸣器** — 水位超标持续报警

自动控制逻辑全部写在从机本地，和网络链路完全解耦。具体的触发规则：

- **烟雾**：50ppm 慢闪 → 100ppm 快闪 → 200ppm 常亮，视觉上就能判断严重程度
- **风扇**：温度超过 30℃、烟雾超过 20ppm、湿度超过 95%，三者满足任一即开启排风
- **排水**：水深超过 75% 打开电磁阀，水位归零后关闭，中间区间保持当前状态不做反复切换
- **补光**：光敏检测到过暗自动点亮照明灯

蜂鸣器特别加了一道防抖——水位必须连续三次超标才触发，避免水面波动造成的反复报警。

### 2.3 手动模式：云端指令和本地自动怎么共存

这是整个从机设计里最微妙的一环。如果云端下发了"关闭风扇"，而下一秒本地自动逻辑检测到高温又把风扇打开，两者就会打架。

解决方案是一个简单的**超时回退机制**：收到云端控制指令后，从机进入"手动模式"，暂停本地自动判断，同时启动一个约 30 秒的计时器。30 秒内如果没有新的云端指令到来，自动退回自动模式。这个设计让远程遥控和本地自保互不干扰，既满足了人工介入的需求，也守住了安全底线。

## 3. 主机：串口进来，MQTT 出去

主机的编程难度不在控制逻辑，而在**通信调度**——它要同时处理三件事：收从机数据、刷 OLED 屏幕、和 ESP8266 对话。

### 3.1 数据接收与显示

从机每隔两秒发一帧数据上来，自定义格式，帧头 `@`、帧尾 `\r\n`，中间是逗号分隔的键值对，一帧包含 10 个字段——烟雾、温度、湿度、水深，加上风扇、电磁阀、两个 LED、蜂鸣器的开关状态，以及当前的手动/自动模式标志。

主机收到完整帧后一次性解析，解析成功就更新 OLED 显示——不仅显示数值，还用图标标记每个执行器的运行状态。哪台设备开着、哪个报警触发、当前什么模式，一目了然。

### 3.2 云端上下行

主机通过 ESP8266 AT 固件连接 WiFi，走 MQTT 协议对接 OneNET。数据上报分三段发送——传感器数据一组、状态数据一组、风扇电磁阀一组，每段之间加一秒延时，避免 ESP8266 的 AT 指令缓冲区溢出。

下行方向，主机在主循环里轮询 ESP8266 的串口响应行，一旦匹配到 MQTT 订阅接收标记，立即提取 JSON 内容解析出目标属性值，拼成控制指令转发给从机。整个过程是非阻塞的——不会因为等云端消息而卡住显示刷新或数据上报。

## 4. 视觉节点：ESP32-CAM 的"眼"

环境数据只能告诉你机房冷不冷、湿不湿，但看不到**有没有人**。加一个摄像头节点，用 ESP32-S3 + OV2640 做了图像采集，配合自建的 YOLO 服务器做了人员检测。

### 4.1 两个 FreeRTOS 任务跑双核

ESP32 是双核芯片，天然适合任务拆分：

**主任务**绑定在核心 0，以最高帧率从 OV2640 抓 RGB565 图像送 ST7789 LCD 实时显示。每抓满 60 帧，抽一张用软件编码压成 JPEG，通过互斥锁塞进共享缓冲区。

**上传任务**绑定在核心 1，独立轮询共享缓冲区。取到图像后 HTTP POST 到 YOLO 服务器，等云端推理完返回人数，再通过 MQTT 上报 OneNET。

两个任务之间严格通过互斥锁同步——主任务发现有旧帧还挂在缓冲里没被取走，直接丢弃覆盖，不会因为上传慢而阻塞采集。这在嵌入式里就是经典的"生产者-消费者"模型。

### 4.2 为什么不在 ESP32 上跑模型

ESP32-S3 虽然带了一点向量加速指令，但距离能跑 YOLO 还差着数量级。云端推理是唯一的选择——搭一台有 GPU 的 Linux 服务器，部署 YOLO 目标检测服务，暴露一个简单的 HTTP 接口：收 JPEG，返回 JSON（人数、置信度）。ESP32 的职责只是"拍照、上传、转发结果"。

## 5. OneNET：免费的云中枢

物联网项目最难的不是写代码，而是**数据存在哪、怎么让手机看到**。自建后端服务器太折腾，OneNET Studio 给免费额度，刚好覆盖整个系统的需求。

### 5.1 物模型就是"数据合同"

在 OneNET 上定义物模型，本质上就是提前约定好每个数据字段的名字和类型——温度叫 Temp、湿度叫 Humi、风扇叫 Fun。硬件按约定上报，网页按约定读取，中间不需要任何格式协商。

| 字段 | 类型 | 含义 |
|------|------|------|
| Temp / Humi | float | 温湿度 |
| MQ2 | int32 | 烟雾浓度 ppm |
| Deep | float | 水位百分比 |
| Fun / Valve / LED1 / LED2 / Buzzer | bool | 执行器状态 |

### 5.2 双向数据流

上行方向很简单：硬件 MQTT 发布 → OneNET 存储。下行方向多绕一小步：网页调 OneNET 的 HTTP API 下发属性 → OneNET 通过 MQTT 推送至 ESP8266 → 主机解析 → 从机执行。链路看起来长，但延迟在秒级，对开关控制来说完全够用。

## 6. 应用端：一套代码，两个平台

### 6.1 PC 网页：纯前端 Serverless

用原生 HTML + Tailwind CSS + Chart.js 写了一个完整的监控后台，六个页面：

- **仪表盘** — 传感器卡片 + 控制器开关 + 设备在线状态 + 异常警报横幅
- **监测** — Chart.js 折线图，24 小时趋势一目了然
- **控制** — 远程开关风扇/电磁阀/灯光/蜂鸣器，执行日志可追溯
- **历史** — 分钟级采样数据表，一键导出 CSV
- **报警** — 异常事件按时间记录，未读已读标记
- **设置** — OneNET 参数配置 + 自定义数据模型

没有任何后端服务器——页面直接浏览器端调用 OneNET 的 HTTP API，配置和数据都存在浏览器的 `localStorage` 里。部署只需要扔到 Vercel 或者任何静态托管平台，几秒钟就能上线。

### 6.2 动态数据模型

传统做法是传感器种类一改就得改代码。我设计了一个配置驱动的方案：在设置页里自由添加传感器和控制器——填上名称、选个图标和颜色、绑定 OneNET 的标识符、设阈值上下限——首页和控制页就会自动渲染出对应的卡片。换一套设备只需要在页面上重新配置，一行代码都不用动。

### 6.3 Android App：原生壳 + Web 心

App 走了 Kotlin + WebView 的混合路线。原生层只做三件事：加载 `assets` 里的 Web 页面、用 `JavascriptInterface` 桥接原生文件分享、适配状态栏和安全区。核心监控逻辑完全复用 PC 端的同一套 Web 代码。

这样更新页面不用重新打包 APK，改完 HTML 直接替换 `assets` 目录即可。唯一需要写原生代码的场景就是 CSV 导出——WebView 里下载文件体验很差，所以通过 `FileProvider` + `Intent.ACTION_SEND` 调用系统分享面板，直接发给微信或者另存到本地。

### 6.4 报警不轰炸

阈值触发报警很简单，难得是怎么不烦人——传感器读数可能在阈值附近抖动，如果不加过滤，用户一分钟能收到十条"恢复-再报警"的消息轰炸。

我用状态机做了消抖：传感器超阈值后立刻记录报警，但同时把该传感器的报警状态标记为"已触发"。五分钟内同一传感器再次超阈值不重复记录。只有先恢复正常、再次超出，才触发新的报警。用简单的状态管理换回了干净的报警列表。

## 7. 回头看：几个设计决策

**为什么把自动控制放在从机而不是云端？** 因为安全逻辑不能依赖网络。如果烟雾报警要经过"传感器→主机→WiFi→云→判断→下发→执行"这一整条链路，中间任一环节断了都会失效。放在从机本地，延迟从秒级降到微秒级，可靠性从"取决于 WiFi 信号"变成"取决于一段 C 代码"。

**为什么要做主从分离？** 如果每个监控点位都配一个 ESP8266，成本翻倍不说，WiFi 信道的竞争也是问题。一根串口线传数据，一个 ESP8266 统一上云，省钱还稳定。

**为什么要搞动态数据模型？** 硬编码的页面在项目初期确实快，但一旦传感器变了、字段名改了、加了新设备，改代码的成本远大于改配置。动态模型本质上是把"变的部分"从代码里剥离到配置里，用一次 UI 设计换来了长期的灵活性。

**为什么 App 用 WebView 而不是原生？** 同一套监控逻辑在 Web 端已经写好了，用 Kotlin 原封不动再写一遍毫无意义。WebView 复用 Web 代码，开发量减半，更新也不用走应用商店审核。

**硬件部分最大的体会是什么？** PCB 设计最容易踩的坑不是原理图，而是封装。第一次打板回来，排针间距偏了半个毫米插不进去，继电器焊盘画反了导致常开常闭接反，DHT11 走线太靠近 WiFi 天线干扰大了读数乱跳。改了三版才稳定下来。焊接也是——MQ2 的模拟输出对电源噪声敏感，后来在 ADC 输入端加了 π 型滤波才把数值稳在 ±2ppm 以内。这些经验在课堂上学不到，只有亲手把板子焊出来、烧进去代码、看着 OLED 刷出第一行数据的时候，才会真正理解"软硬件联调"这四个字的份量。

## 8. 坦率讲，还有很多不足

项目跑起来了，但回顾整个过程，值得改进的地方不少。

**传感器选型偏低端。** DHT11 的温湿度精度只有 ±2℃ 和 ±5%，对于机房监控来说勉强够看但不体面。MQ2 烟雾传感器的预热时间长、一致性差，长期漂移也明显。如果条件允许，升级成 SHT30 + PMS5003 会是质变。

**ESP8266 走 AT 固件太受罪。** 主机通过 AT 指令和 ESP8266 交互，串口速率 115200，MQTT 数据一多就容易丢帧。AT 指令的响应格式也不够结构化，解析出错时很难定位是 WiFi 问题还是模块问题。换成 ESP32 自己跑 MQTT Client 固件，或者直接用内置 WiFi 的 STM32 系列，通信稳定性会好很多。

**本地没有数据缓存。** 如果 WiFi 断线，断网期间的数据直接丢失——主机没接 SD 卡，没有任何本地存储机制。哪怕加一个 8MB 的 SPI Flash 做环形缓冲，断网期间的数据也能在恢复后补传。

**ESP32-CAM 的软件 JPEG 编码太慢。** 每 60 帧抽一帧是因为编码一帧 JPEG 就要花掉上百毫秒。实际上 ESP32-S3 是有硬件 JPEG 编码器的，只是当时没用到。如果把这部分改为硬件编码，抽帧频率可以大幅提高。

**CSV 导出依赖浏览器缓存。** 历史数据存在 `localStorage` 里，容量上限大约 5-10MB，满打满算只能存几天数据。正经做法要么接一个轻量后端存数据库，要么利用 OneNET 的历史数据查询 API 按需拉取。

**没有 OTA 固件升级。** 设备装到现场后如果要改固件，必须拆下来拿 ST-Link 烧录。ESP32 其实原生支持 OTA，但在项目规划阶段没把这个需求考虑进去，现在补代价不小。

**安全方面几乎是裸奔。** YOLO 服务器的 HTTP 接口没有鉴权，OneNET Token 明文写在配置里，前端页面的管理员密码也比较弱。学生项目阶段可以接受，但如果要长期部署，这些都得上加固。

这些不足我列在这里，不是自我批评，而是提醒自己——一个能跑的项目和一个好项目之间，差的就是这些细节。以后迭代的方向也在这儿。
