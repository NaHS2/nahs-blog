# 从零搭建分布式机房监控系统：STM32 + ESP32 + OneNET 云 + 全平台应用

机房环境对温湿度、烟雾、浸水等因素极为敏感，一旦出现异常而未及时发现，轻则设备故障，重则引发火灾。市面上成熟的动环监控方案动辄上万元，对于学校实验室或小型机房来说成本太高。于是我自己设计了一套**分布式机房监控系统**——从底层传感器采集到云端数据中转，再到桌面和手机端的监控应用，完整覆盖了物联网项目的全链路。

> 这篇文章分享整个系统的设计思路和实现方法，不涉及具体代码细节。

---

## 1. 系统总览

整个项目的硬件架构采用了**一主一从 + 视觉节点**的分布式设计：

```
┌─────────────────────────────────────────────────┐
│                   OneNET 云平台                    │
│              (MQTT 数据中转 + 物模型)               │
└────────┬──────────────┬──────────────┬───────────┘
         │ MQTT         │ MQTT         │ HTTP/MQTT
    ┌────┴────┐    ┌────┴────┐    ┌───┴────┐
    │ STM32主机 │    │ ESP32   │    │ PC网页  │
    │ (数据汇聚)│    │ (AI视觉) │    │ + App   │
    └────┬────┘    └─────────┘    └────────┘
         │ USART
    ┌────┴────┐
    │ STM32从机│
    │ (传感器) │
    └─────────┘
```

| 层级 | 硬件 | 职责 |
|------|------|------|
| 采集层 | STM32F103C8T6（从机） | 驱动 6 类传感器 + 5 种执行器，运行自动控制逻辑 |
| 汇聚层 | STM32F103C8T6（主机） | 接收从机数据、OLED 显示、ESP8266 WiFi 上云、云端指令下发 |
| 视觉层 | ESP32-S3 + OV2640 | 图像采集并上传至自建 YOLO 服务器做人员检测 |
| 应用层 | PC 网页 + Android App | 实时数据监测、图表分析、远程控制、报警管理 |

---

## 2. 硬件层：一主一从的 STM32 双 MCU 架构

设计成主从架构的原因是：从机放在机房内部，专注于传感器采集和本地联动控制；主机放在有 WiFi 信号的位置，负责云平台通信。两者通过 USART 串口互联，只传一根线。

### 2.1 从机：传感器采集与本地自动控制

从机连接了六种传感器和五种执行器：

**传感器：**
- DHT11 — 温湿度采集
- MQ2 — 烟雾浓度检测（ppm）
- HW038 — 水位传感器（百分比换算）
- 光敏电阻 — 环境光照检测
- ADC 多通道 — 模拟信号采集

**执行器（继电器 + GPIO 控制）：**
- 排风扇 — 温度过高或烟雾超标时自动开启
- 电磁阀 — 水位过高时自动排水
- LED1 — 烟雾浓度分级报警（闪烁频率随浓度递增）
- LED2 — 环境过暗时自动补光
- 蜂鸣器 — 水位超标连续报警（带防抖计数）

从机的核心设计在于**自动控制逻辑**——即使断网、即使主机离线，本地保护依然有效：

- **烟雾报警**：50ppm 慢闪 → 100ppm 快闪 → 200ppm 常亮
- **风扇联动**：温度 > 30℃ 或烟雾 ≥ 20ppm 或湿度 ≥ 95%，自动开启排风扇
- **水位排水**：水深 > 75% 开启电磁阀排水，降至 0 时自动关闭
- **补光灯**：环境光照不足时自动点亮

从机同时支持**手动模式**——云端下发控制指令后，从机进入手动模式并暂挂自动逻辑，约 30 秒无新指令自动恢复自动模式。这个设计避免了云端指令和本地自动控制之间互相冲突。

### 2.2 主机：数据汇聚与云平台桥接

主机的职责更偏"通信"：

1. 通过 USART1 接收从机上报的传感器数据包（自定义帧格式，帧头 `@`，帧尾 `\r\n`）
2. 解析数据后在 OLED 上实时显示各项指标和设备运行图标
3. 通过 ESP8266 WiFi 模块连接互联网，走 MQTT 协议将数据分段上传至 OneNET 云平台
4. 同时订阅云端下发的控制指令，解析后转发给从机执行

主机的 ESP8266 驱动采用了**非阻塞**设计——在主循环中轮询串口缓冲区，读到 MQTT 下行消息后立即解析处理，不阻塞正常的显示刷新和数据上报流程。

### 2.3 通信协议设计

从机到主机的数据帧格式：

```
@SMOKE=45.20,TEMP=28,HUMI=65,DEEP=30.50,FAN=1,LED1=0,LED2=1,BUZZER=0,VALVE=0,MODE=0\r\n
```

10 个字段，逗号分隔，键值对格式。主机用 `sscanf` 一次性解析，解析失败会在 OLED 上显示错误提示。

主机到时隙的下行控制指令：

```
CTRL:LED1=1,LED2=0,BUZZER=0,FAN=1,VALVE=0
```

从机收到后直接操作对应 GPIO，同时进入手动模式。

## 3. 视觉节点：ESP32-CAM + YOLO 人员检测

除了环境监测，系统还加入了**机房人员检测**功能。硬件使用了 ESP32-S3 开发板 + OV2640 摄像头 + ST7789 SPI LCD 屏。

### 3.1 双任务架构

ESP32 上跑了两个 FreeRTOS 任务：

**主任务（图像采集 + LCD 刷新）：**
- 以尽可能高的帧率从 OV2640 读取 RGB565 图像
- 实时送至 SPI LCD 显示（本地预览）
- 每 60 帧抽一帧，用软件编码压缩为 JPEG（质量 80）
- 通过互斥锁将压缩后的图像交给上传任务

**上传任务（云端分析 + OneNET 上报）：**
- 独立轮询，从互斥锁保护的共享缓冲区取走最新的 JPEG
- HTTP POST 上传至自建的 YOLO 目标检测服务器
- 解析返回的 JSON 结果，提取画面中的人数
- 将人数通过 MQTT 上报至 OneNET 平台

两个任务共享一块图像缓冲区，通过 FreeRTOS 互斥锁保护。上传任务取走图像后释放内存，主任务发现有旧帧未被取走时直接丢弃并覆盖——这是一个典型的"生产者-消费者"模式，保证了 CPU 资源紧张的 ESP32 上不会因上传阻塞导致采集掉帧。

### 3.2 自建 YOLO 服务器

考虑到 ESP32 的算力远不足以运行神经网络，云端推理是唯一的可行方案。搭建了一台带 GPU 的服务器，运行 YOLO 目标检测模型，对外暴露 HTTP 接口——接收 JPEG 图片，返回 JSON 格式的检测结果（检测到的人数、置信度等）。ESP32 将图片上传后，解析返回结果再通过 MQTT 转发到 OneNET。

## 4. 云平台：OneNET Studio 物模型

整个系统的数据中枢选用了中国移动的 **OneNET Studio** 物联网开放平台。选择理由很简单：免费额度对学生项目足够、MQTT 协议成熟稳定、提供完整的物模型和 API。

### 4.1 物模型设计

在 OneNET 上定义了完整的物模型属性：

| 标识符 | 类型 | 描述 |
|--------|------|------|
| Temp | float | 温度（℃） |
| Humi | float | 湿度（%） |
| MQ2 | int32 | 烟雾浓度（ppm） |
| Deep | float | 水深百分比（%） |
| Fun | bool | 风扇状态 |
| Valve | bool | 电磁阀状态 |
| LED1 | bool | 报警灯状态 |
| LED2 | bool | 照明灯状态 |
| Buzzer | bool | 蜂鸣器状态 |

### 4.2 数据流

上行链路：从机采集 → 主机封装 → ESP8266 MQTT 发布 → OneNET 存储

下行链路：Web/App 调用 OneNET API 下发属性设置 → OneNET 推送 MQTT 消息到 ESP8266 → 主机解析 → 从机执行

## 5. 应用层：PC 网页 + Android App

应用端采用了一套代码、两个平台的策略。

### 5.1 PC Web Dashboard

纯静态前端页面（HTML + Tailwind CSS + 原生 JS），零后端依赖，通过 OneNET 官方 API 直连云平台。六个功能页面：

- **仪表盘首页** — 所有传感器和控制器的概览卡片，设备在线状态指示，环境异常警报横幅
- **环境监测** — 基于 Chart.js 的实时折线图，展示各传感器 24 小时变化趋势
- **设备控制** — 开关类控制（风扇、电磁阀、灯光、蜂鸣器），操作日志记录
- **历史数据** — 数据表格展示，支持 CSV 一键导出
- **报警记录** — 异常事件自动记录与列表管理
- **系统设置** — OneNET 平台参数配置、数据模型动态管理

### 5.2 动态数据模型

传统 IoT 监控页面往往是硬编码的，换一套传感器就得改代码。这个系统设计了一个**完全动态的数据模型**：

在设置页面，用户可以自由添加/删除/编辑传感器和控制器的定义——包括名称、OneNET 标识符映射、图标、主题色、单位、数据类型、阈值上下限。首页和控制页会根据数据模型自动渲染对应的卡片和开关。

所有配置存储在浏览器的 `localStorage` 中，不需要后端数据库，满足了纯前端部署的需求。

### 5.3 Android App

Android 端采用了 **Kotlin + WebView** 的混合架构——原生外壳提供文件分享、安全区适配等平台能力，核心业务逻辑复用 PC 端的整套 Web 代码，打包在 `assets/www/` 下通过 WebView 加载。

这样做的好处是显而易见的：更新 Web 页面不需要重新发版 APK，只需更新 `assets` 目录下的 HTML/JS/CSS 文件即可。同时通过 Kotlin 的 `JavascriptInterface` 桥接，Web 端可以调用原生的文件分享功能——把历史数据导出为 CSV 后直接拉起系统分享面板，发送到微信或保存到本地。

### 5.4 报警系统

应用端内置了一套**状态机过滤机制**来抑制误报。因为网络波动可能让数据短暂到达阈值后又恢复正常，如果每次都弹警报，用户体验会很差。

设计思路是：传感器超过阈值后，进入"报警挂起"状态，如果 5 分钟内再次检测到同一传感器超阈值，不重复记录。只有当指标恢复正常并再次超阈值，才触发新的报警。报警记录保存在 `localStorage` 中，支持查看历史。

## 6. 系统亮点

**本地 + 云端双重保障。** 从机的自动控制逻辑独立于网络——即使完全断网，烟雾超标时排风扇依然会启动，水位过高时电磁阀依然会排水。云端更多用于远程监看和手动干预。

**分层解耦。** 主从机各自职责明确，通过简单的串口协议通信。一端出问题不会导致整个系统瘫痪。

**零成本运行。** OneNET 免费额度足以支撑每分钟一次的数据上报，PC Web 端是纯静态页面可以部署在 Vercel/GitHub Pages 上，服务器端只有 YOLO 推理需要一台带 GPU 的机器。

**动态可扩展。** 数据模型驱动的 UI 设计，新增传感器不需要改前端代码，在设置页配置即可。
