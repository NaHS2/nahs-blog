# 给老款电动车加上一套完整的物联网系统：ESP32、4G网关、Android App与管理后台

> 参考源码：[github.com/NaHSIT/electric_vehicle](https://github.com/NaHSIT/electric_vehicle)  
> 仓库为脱敏版本，已移除个人隐私、生产凭据及线上基础设施信息，保留完整的系统架构、通信协议与工程实现，适合作为物联网车辆控制系统的参考。

这次做的不是一个“手机蓝牙控制器”，而是一套围绕老款小牛 G0 电动车搭起来的完整系统：车上有 ESP32-S3 控制器和 M100MG-B1 4G/定位模块，手机上有 Android App，服务器上有 TCP 设备网关和 HTTP API，浏览器里还有一个管理后台。

项目最后形成了四条彼此配合的链路：蓝牙负责近距离控制，4G 负责远程控制和数据上报，服务器负责保存状态与轨迹，手机热点负责本地 Wi‑Fi OTA。把它们拆开看，每一部分都不算陌生；真正困难的是让这些模块在网络断开、数据半包、设备重连和升级失败时仍然保持一致。

本文不只介绍“用了哪些库”，而是从需求、分层、协议、状态管理到安全边界，把这个项目的设计思路完整记录下来。

---

## 1. 先把需求说清楚：这不是给车装一个按钮

项目面对的是一辆老款电动车。它原本已经具备基本的车辆电气系统，但缺少一个可以被手机和服务器理解的数字控制层。因此需求分成四组。

### 1.1 车辆侧需求

- 近距离通过蓝牙锁车、解锁和读取状态；
- 远距离通过 4G 接收锁车、解锁、找车等命令；
- 控制车辆电源、继电器和蜂鸣器；
- 上报锁定模式、车辆电源、4G 状态、模块就绪状态和 OTA 状态；
- 连接 GPS/北斗模块，保存最后一次有效位置；
- 只在车辆解锁并实际运行时累计里程；
- 设备断电或网络断开后，重新连接能够恢复工作。

### 1.2 手机 App 需求

- 车辆页显示 3D 车辆和当前锁定状态；
- 蓝牙可用时走近场控制，蓝牙不可用时仍能通过云端找车；
- 地图区分“人”和“车”，显示最后位置、轨迹、距离和分享入口；
- 设备页查看 4G、RDY、继电器、OTA 等硬件状态；
- 保存设备名称、蓝牙密码和手机热点信息；
- 从服务器选择已发布固件，并通过手机热点把固件传给 ESP32。

### 1.3 服务器与后台需求

- 接收 4G DTU 的 TCP 透传数据；
- 解析 GPS、状态帧和原始模块数据；
- 保存设备状态、位置历史、轨迹、里程和事件；
- 提供 App 和后台都能调用的 HTTP API；
- 管理员能够查看车辆、远程控制、找车和查看轨迹；
- 支持固件上传、SHA-256 校验、发布、下载和删除；
- 设备掉线后不能继续显示“假在线”。

### 1.4 非功能需求

车辆控制最看重可靠性，地图最看重数据时效性，OTA 最看重完整性，后台最看重权限边界。这几个目标有时会互相冲突，所以系统不能只追求“功能能跑”，还要明确每条链路允许怎样失败。

例如，地图暂时拿不到新 GPS 时可以显示最后一次有效位置；但锁车命令不能仅仅因为 HTTP 返回 200 就显示成功，还需要等待设备回传状态确认。

## 2. 总体架构：四个角色，三种通信方式

整个系统可以抽象成下面这条数据流：

```text
手机 App ── BLE ── ESP32-S3 ── UART ── M100MG-B1 ── TCP ── 云端网关
   │                                      │                  │
   ├──────────── HTTPS/JSON API ──────────┘                  ├─ 状态/位置/轨迹
   │                                                         ├─ 远程命令
   │                                                         └─ 固件目录
   │
   └──── 手机热点 Wi‑Fi ─── ESP32 本地 OTA

管理员浏览器 ───────────── HTTPS/JSON API ─── 云端网关
```

这里有三个关键分工。

第一，ESP32 不直接访问地图、数据库或复杂的云服务，它只关心 GPIO、蓝牙、串口和车辆状态。第二，4G DTU 不负责理解完整业务，只负责把 ESP32 的串口数据带到服务器。第三，业务语义集中在网关和 App 中，避免把“锁车”“找车”“版本发布”这些概念硬编码在每一层。

这是一种典型的边缘设备分层：

| 层次 | 主要组件 | 负责什么 |
| --- | --- | --- |
| 执行层 | ESP32-S3、继电器、蜂鸣器 | 把命令变成真实电平和动作 |
| 连接层 | M100MG-B1、UART、TCP | 建立蜂窝网络并传输数据 |
| 服务层 | Python 网关、HTTP API | 解析、保存、转发和校验 |
| 交互层 | Android App、Web 后台 | 展示状态、发起操作和管理版本 |

## 3. ESP32-S3：把车辆动作封装成可验证的状态机

### 3.1 为什么选 ESP32-S3

ESP32-S3 同时具备 GPIO、蓝牙、Wi‑Fi、串口和足够的 Flash/RAM，既能做近距离 BLE 控制，也能处理 4G 模块的 UART 数据，还可以在升级时暂时启动本地 Wi‑Fi 服务。相比用一个只会控制继电器的单片机，ESP32 更适合做这层“车辆控制器”。

工程使用 PlatformIO 管理，框架是 Arduino，目标板为 `esp32-s3-devkitc-1`。PlatformIO 的价值不只是“一键编译”，还把板卡、框架、分区表、串口监视和依赖库统一放进 `platformio.ini`，后续换电脑时不需要重新手工拼装工程。

### 3.2 引脚不是随便挑的

当前主要连接关系如下：

| ESP32 引脚 | 功能 | 设计含义 |
| --- | --- | --- |
| GPIO17 | ESP32 TX | 发送到 M100 RXD |
| GPIO18 | ESP32 RX | 接收 M100 TXD |
| GPIO8 | DTR | 唤醒或保持 4G 模块 |
| GPIO9 | RDY | 读取模块是否就绪 |
| GPIO4 | 车辆电源 | 控制车辆电源输出 |
| GPIO5 | 小蜂鸣器 | 本地提示 |
| GPIO6 | 大蜂鸣器继电器 | 远程找车声光动作 |
| GPIO48 | RGB LED | 显示连接、OTA 和异常状态 |

UART 必须交叉连接：ESP32 的 TX 接模块 RX，ESP32 的 RX 接模块 TX。M100 的 RST 在当前硬件方案中保持不接，因为错误地控制它会让模块进入异常状态。硬件问题不能靠软件“多重试几次”解决，首先要把电源、电平、天线和引脚关系确认清楚。

### 3.3 代码按职责拆分

固件没有把所有逻辑堆在 `main.cpp` 中，而是拆成几个明确的模块：

- `vehicle_state`：保存锁定模式、车辆电源、找车和里程等状态；
- `ble_controller`：处理蓝牙服务、特征值、连接和命令回传；
- `air_controller`：通过 UART 与 M100 通信，解析远程命令和定位数据；
- `wifi_ota_controller`：启动热点、接收固件和执行本地 OTA；
- `status_led`：把状态映射成 RGB 指示灯效果；
- `main`：初始化模块并驱动主循环。

这种拆分的核心不是文件看起来整齐，而是让“硬件动作”和“通信入口”解耦。蓝牙收到 `LOCK`，4G 收到 `REMOTE_LOCK`，最终都应该调用同一个车辆状态函数，而不是分别复制一套继电器操作。

### 3.4 命令不等于状态

命令是瞬时事件，状态是持续事实。比如：

```text
REMOTE_UNLOCK  →  执行解锁动作  →  mode=UNLOCKED
```

如果只记录“命令发送成功”，手机无法知道车辆到底有没有执行。更稳妥的做法是：命令进入设备后，ESP32 修改内部状态，再发送一条 `STATUS`。服务器和 App 以 `STATUS` 为最终显示依据。

找车也是一样。App 点击找车后，服务器返回的是“命令已发送”，不是“蜂鸣器已经响了”。设备回传 `find=1` 后，UI 才显示找车中；停止找车收到 `find=0` 后再恢复空闲。

### 3.5 UART 解析必须面对半包和粘包

TCP 或串口读取一次，不代表刚好读到一条完整消息。一次读取可能得到半条状态帧，也可能连续得到三条状态帧。因此解析器不能假设每次 `read()` 都是完整数据，而要采用缓冲区：

```text
收到字节 → 追加到缓冲区 → 查找换行符 → 拆出完整记录 → 解析 → 保留剩余半包
```

固件还要处理上电日志、空字节、未知字段和超长记录。解析失败时丢弃当前记录比把错误数据写进车辆状态更安全。

### 3.6 里程统计为什么不能直接累加 GPS 距离

GPS 在车辆静止时也会漂移。如果每次收到坐标都计算距离，车停在楼下也可能慢慢增加里程。因此当前策略是同时加入业务条件和数据过滤：

1. 只有车辆处于解锁运行状态时才累计；
2. 丢弃无效的 `0,0` 坐标；
3. 过滤距离过小的抖动；
4. 拒绝速度和跳点明显异常的坐标；
5. 保存上一次有效点，再计算相邻点距离。

这说明传感器数据不是“收到就可信”，业务状态和物理约束必须一起参与判断。

## 4. M100MG-B1：4G 与定位模块只是传输层

M100MG-B1 提供 Cat.1 蜂窝网络和 GPS/北斗定位能力，ESP32 通过 TTL UART 与它通信。它的职责是连接网络、接收服务器数据、把服务器数据透传给 ESP32，并把设备产生的数据反向送回服务器。

项目没有把业务逻辑塞进 DTU 配置里，而是在 ESP32 和服务器两端解析文本协议。这样做的好处是：

- 车辆状态的定义由自己的代码控制；
- 模块更换时，只需适配 UART 和连接参数；
- 服务器能够保存原始帧，出现问题时可以回放；
- TCP 数据和串口数据都可以用相同的记录格式处理。

服务器端还开启 TCP keepalive，并对唯一设备的重复连接做保护。4G 网络切换时可能留下半开连接，如果不清理，后台会认为设备仍然在线，新的真实连接也可能被旧连接占用。

定位解析则兼容多种来源格式：固定格式经纬度、逗号分隔坐标、带 `N/S/E/W` 方向的坐标以及模块扩展上报格式。经度和纬度的方向符号必须转换成带正负号的十进制度，南纬和西经不能直接当成正数。

## 5. Python 云端网关：一端 TCP，一端 HTTP

服务端核心文件是 `vehicle_gateway.py`。它同时承担两个方向的工作：

- TCP 监听设备连接，接收位置、状态和原始数据；
- HTTP 提供 App 与管理后台调用的 JSON API。

设备接入使用 `asyncio`，适合等待网络数据；HTTP 接口使用线程化服务器处理请求。两者之间通过共享状态、连接表和事件循环通信：HTTP 收到远程命令后，把发送任务投递到 TCP 事件循环，等待设备连接写入命令。

### 5.1 为什么网关要保存状态

App 不应该每次打开都直接询问设备，因为设备可能暂时离线、正在切换基站或 GPS 尚未定位。网关保存以下信息：

- `last_seen`：最后一次通信时间；
- `hardware_status`：最近一次硬件状态；
- `last_location`：最后一次有效位置；
- `track`：位置历史；
- `events`：锁车、解锁、找车和状态变化事件；
- `last_data`：最近的原始数据片段；
- `ota`：升级任务状态。

当前项目用 JSON 文件持久化，优点是依赖少、调试直观、单车项目足够；缺点是并发能力、查询能力和历史数据规模有限。未来如果设备数量增加，应该把设备状态、轨迹和事件迁移到 SQLite 或 PostgreSQL，并给轨迹表增加时间和设备索引。

### 5.2 “在线”是一个时间判断

TCP 连接存在不等于设备仍然在线。设备可能断电、移动到无信号区域，或者连接已经半开。因此在线状态至少要结合：

```text
connected = TCP连接存在 AND 当前时间 - last_seen < 超时阈值
```

断开时立即标记离线，轮询状态时再次根据 `last_seen` 校正。UI 不应该永远相信历史上某一次 `connected=true`。

### 5.3 API 设计按资源和动作区分

网关的接口可以分为几类：

- 设备摘要：读取车辆列表、硬件状态和最后位置；
- 轨迹接口：按设备读取位置历史；
- 控制接口：锁车、解锁、找车和停止找车；
- 原始数据接口：读取或下发调试帧；
- 固件接口：上传、发布、下载和删除版本；
- 健康检查：检查 API 和 TCP 监听是否正常。

控制类接口还要限制请求频率，避免网络抖动或重复点击造成连续继电器动作。服务端返回“命令已发送”和设备最终状态是两个不同概念，客户端需要按状态轮询或接收后续上报。

## 6. Android App：Compose 负责界面，ViewModel负责状态

### 6.1 技术栈

Android 工程使用 Kotlin、Jetpack Compose、Material 3、Lifecycle ViewModel 和 DataStore。地图使用百度 Android 地图 SDK，3D 车辆使用 SceneView、Filament 和 GLB 模型，蓝牙和 Wi‑Fi OTA 使用 Android 系统 API。

选择 Compose 的原因是状态驱动的界面更适合这个项目。车辆状态、蓝牙连接、地图数据和 OTA 进度都会变化，如果仍然在大量 XML View 上手动 `setText()`、`setVisibility()`，很容易出现数据更新了但页面没有同步的问题。

### 6.2 ViewModel 是界面与业务的边界

App 按功能拆出多个 ViewModel：

- `VehicleViewModel`：车辆控制和车辆摘要；
- `HardwareStatusViewModel`：硬件状态展示；
- `LocationViewModel`：人车位置、轨迹和距离；
- `RemoteOtaViewModel`：版本选择、升级阶段和进度；
- `RawModuleDataViewModel`：原始模块帧查看与下发。

页面只订阅状态并渲染 UI，按钮点击则调用 ViewModel 的动作函数。这样页面旋转、返回再进入或重新组合时，业务状态不会全部丢失。

### 6.3 蓝牙控制与 4G 控制如何共存

蓝牙是低延迟近场通道，适合车在身边时使用；4G 是高延迟远程通道，适合找车、查看位置和远程控制。两者不应该在 UI 上伪装成同一种实时连接。

一个合理的控制流程是：

```text
用户点击按钮
  ↓
判断蓝牙是否可用
  ├─ 可用：写 BLE 特征值，等待 ESP32 状态回传
  └─ 不可用：调用 HTTPS API，由网关转发到 4G，再轮询最新状态
```

无论入口是哪一条，最后都归一到同一个车辆状态模型。UI 展示的是 `LOCKED`、`UNLOCKED`、`FINDING` 等业务状态，而不是简单展示“某个按钮被点击过”。

### 6.4 3D 车辆不是装饰，而是状态载体

车辆 GLB 模型放在 App 的 assets 中，由 SceneView/Filament 加载。3D 场景主要解决两个问题：让车辆页有明确的主体，也让锁定、解锁、加载和异常状态能够通过颜色、动画或标签表达。

但 3D 渲染不能影响控制链路。模型加载失败时，锁车和状态读取仍然应该可以执行；渲染线程卡顿时，后台的状态轮询也不应该停止。视觉层必须是业务层的消费者，而不是业务层的前提条件。

### 6.5 地图需要区分“位置来源”和“位置时效”

地图同时显示手机位置和车辆位置。手机位置来自 Android 定位能力，车辆位置来自服务器保存的 GPS/北斗数据。两者的来源、刷新频率和可信度都不一样，因此界面要明确显示：

- 车辆是否在线；
- 车辆位置更新时间；
- 这是实时位置还是最后有效位置；
- 轨迹是哪一段时间产生的。

没有有效 GPS 时不能把 `0,0` 当成非洲海上的真实车辆位置，也不能用手机位置冒充车辆位置。这个边界在物联网地图里非常重要。

### 6.6 DataStore 保存的是配置，不是设备事实

DataStore 适合保存设备名称、蓝牙密码、热点 SSID 和用户偏好这类本地配置。车辆锁定状态、在线状态和 GPS 位置仍然应该来自设备或服务器，不能把上一次页面显示的值当作真实状态。

## 7. OTA：为什么最终选择手机热点 + Wi‑Fi

固件更新是这个项目里最容易“看起来成功，实际上变砖”的部分。早期方案尝试过把固件经 4G TCP 透传到车辆，但大二进制经过 DTU 缓冲、转义和分包后，可靠传输非常困难；如果只在 UI 上推进进度条，无法证明设备真的写入了完整镜像。

当前正式方案分成两条链路：

1. 服务器只负责保存固件、计算 SHA-256、发布版本和供 App 下载；
2. 手机打开热点，App 让 ESP32 连接该热点，通过本地 Wi‑Fi 把固件传给 ESP32。

这相当于把“远程选择版本”和“近距离传输大文件”分开。4G 仍然用于车辆控制和状态上报，但不承担大文件 OTA。

### 7.1 OTA 的完整状态机

```text
idle
  → preparing       检查版本、大小和 SHA-256
  → hotspot_ready   配置或连接手机热点
  → device_connected 找到 ESP32 OTA 服务
  → transferring    分块发送固件
  → verifying       ESP32 校验写入结果
  → completed       重启并回传新版本
```

任何阶段失败都应该进入 `failed`，并关闭热点连接或恢复车辆控制服务。客户端不能只根据“HTTP 上传完成”判断成功，必须等待 ESP32 的最终确认。

### 7.2 为什么要做分区表

ESP32 的 OTA 分区一般采用 A/B 两个应用分区：当前固件运行在一个分区，新固件写入另一个分区。写入完成并校验通过后，启动器把下次启动目标切换到新分区；如果新固件启动失败，可以回滚到旧分区。

分区表直接决定最大固件大小，因此项目中使用专门的 `partitions_ota.csv`，不能只把默认分区表换个文件名就结束。固件大小、Flash 地址、升级块大小和回滚策略必须一起验证。

### 7.3 固件发布为什么需要 SHA-256

后台上传固件后先计算 SHA-256，发布时记录版本、大小、哈希和说明。App 下载后再次计算并与目录中的哈希比较，ESP32 写入后还要进行镜像完整性检查。

哈希校验解决的是“文件有没有被截断或损坏”，不等于“发布者身份认证”。如果未来开放给更多用户，还需要签名固件：设备内置公钥，只有通过私钥签名的镜像才允许启动。

## 8. Web 管理后台：纯前端也可以做出完整运维界面

管理后台位于 `admin/index.html`，采用原生 HTML、CSS 和 JavaScript，没有再引入一套前端构建链。后台通过 API 完成登录、车辆列表、地图、远程控制、轨迹和固件管理。

地图使用 Leaflet 加 OpenStreetMap。浏览器端地图和 Android 百度地图是两套不同 SDK，不能把 Android 的 Key 直接拿到网页里用；这是平台密钥作用域不同造成的。

后台的功能设计按照运维流程组织：

1. 总览页先看系统健康和车辆在线状态；
2. 设备页查看硬件明细和发送控制命令；
3. 位置页看最后位置和轨迹；
4. 事件页回看锁车、解锁、找车和状态变化；
5. 固件页上传、校验、发布和下载；
6. 原始数据页用于排查协议和硬件问题。

原始数据页面很有价值。抽象状态告诉我“车辆离线”，原始帧则可能告诉我到底是 4G 没有注册、RDY 没有拉起、GPS 没有定位，还是 ESP32 没有回状态。系统要可维护，就必须给排障留一条从业务状态回到底层帧的路径。

## 9. 安全设计：能控制车辆，就不能只靠一个固定 Token

这个项目涉及车辆控制，安全不能最后再补。当前已经加入了 HTTPS、HttpOnly/Secure/SameSite 会话 Cookie、登录限流、安全响应头、后台写操作的来源校验、固件大小与镜像头校验等措施。

但仍然要清楚几个现实边界。

### 9.1 App 内置 Token 不是秘密

只要 Token 被编译进 APK，就可能被反编译提取。因此它最多只能算“调用凭据”，不能算真正的密钥。商业化方案应改成用户登录、短期访问令牌、设备级权限和控制接口二次确认。

### 9.2 TCP 设备接入必须有设备身份

公网 TCP 端口不能只靠“连上端口就认为是那辆车”。当前协议支持设备注册认证，并对重复连接做保护；更完整的方案应该让每个 DTU 拥有独立密钥，使用类似下面的认证思路：

```text
设备发送 device_id + nonce
服务器返回 challenge
设备计算 HMAC(device_key, nonce)
服务器验证通过后建立会话
```

这样即使别人知道端口，也不能伪造定位、状态或接收远程命令。

### 9.3 控制命令要可追踪

每次锁车、解锁和找车都应该记录操作者、时间、目标设备、命令结果和设备最终状态。出现误操作时，日志要能回答“谁在什么时候发了什么命令，设备有没有确认”。

### 9.4 固件最好走签名验证

SHA-256 只能证明内容完整，不能证明来源可信。下一步可以在发布端使用私钥签名，在 ESP32 固件中内置公钥，设备只接受签名正确、版本号符合策略的镜像，并防止降级到有漏洞的旧版本。

## 10. 调试与验证：按链路分段，不要只测最后的 UI

这类系统最怕“界面看起来能点，底层其实没通”。我把验证拆成五层：

### 10.1 固件层

验证 GPIO 电平、UART 收发、蓝牙特征值、状态机、OTA 分区和编译产物。车辆控制不能只看日志，还要测继电器、电源和蜂鸣器实际动作。

### 10.2 网关层

用单元测试验证坐标解析、里程过滤、状态解析和 OTA 元数据校验。TCP 测试要覆盖半包、粘包、无换行静默刷新、重复连接和断线。

### 10.3 API 层

测试健康检查、登录、设备摘要、控制命令、轨迹、固件上传和发布。控制失败时要确认 HTTP 错误、设备是否收到、状态是否回传三件事，而不是只看返回码。

### 10.4 App 层

验证蓝牙连接与断开、4G 远程控制、地图无定位、最后位置、热点连接、传输中断和 OTA 完成后的版本刷新。

### 10.5 真机层

最后必须在真实车辆和真实网络中验证：4G 基站切换、GPS 冷启动、车辆断电、手机锁屏、热点重连、弱网控制和升级失败恢复。代码编译通过，不能等价于车辆物理链路已经通过。

## 11. 这次项目里最重要的几个取舍

### 11.1 先做稳定的文本协议，再考虑二进制协议

文本协议可读、可抓包、可直接从串口终端调试，适合项目早期和单车规模。它的缺点是效率低、边界容易出错。等设备数量和数据量上升后，再引入明确的长度字段、序列号、校验和和版本号，比一开始就设计一套看不懂的二进制协议更容易验证。

### 11.2 JSON 文件适合原型，不适合无限扩张

单车项目用 JSON 保存状态，打开文件就能看，排查问题很方便。但它不适合高频轨迹、大量设备和复杂查询。数据量上去后，应把“当前状态”“历史轨迹”“事件日志”“固件目录”拆成不同的持久化结构。

### 11.3 OTA 传输链路必须和业务链路解耦

车辆控制追求短消息和及时确认，固件升级追求长数据流和完整校验。让它们共用一条脆弱的透明透传链路，会让两种需求互相拖累。手机热点 OTA 虽然需要车辆在手机附近，但换来了更可控的传输和更容易验证的失败恢复。

### 11.4 UI 状态不能替代设备状态

按钮点击、请求返回、服务器接收、设备执行和设备回报，是五个不同阶段。好的系统会把它们分别表达出来，而不是点击按钮后立刻把车辆画成“已解锁”。

---

## 12. 后续可以怎样继续演进

如果把项目从个人单车工具继续做成可长期运行的产品，下一步会是：

- 使用设备独立密钥和 HMAC/证书认证；
- App 改为用户登录和短期 Token；
- 将 JSON 状态迁移到 SQLite 或 PostgreSQL；
- 给 TCP/业务帧增加序列号、时间戳、校验和与协议版本；
- 增加消息队列或 WebSocket，减少 App 轮询；
- 固件加入签名验证、防回滚和更完整的 A/B 回滚策略；
- 对轨迹进行抽稀、分段和按时间索引；
- 为后台和 App 增加自动化 UI 测试与真机回归清单；
- 增加监控、告警和日志轮转，避免服务器状态文件无限增长。

---

> 这个项目让我真正理解了“物联网系统”为什么不是把几个模块连起来就结束：蓝牙要处理连接状态，4G 要处理半包和断线，GPS 要处理漂移，服务器要处理持久化，App 要处理异步状态，OTA 要处理完整性，后台还要处理权限。每一层单独看都能写出一个小项目，只有把它们放在同一条数据链路上，才会暴露出真正的工程问题。

> 最后留下的也不只是一个能锁车和找车的 App，而是一套从 GPIO 电平、UART 字节，一直走到移动端界面和服务器运维的完整实践。
