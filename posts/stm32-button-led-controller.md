# 四个按键控制两盏LED：从消抖到事件触发

> 源码：[github.com/NaHSIT/STM32ZET6Project/tree/main/projects/03-button-led-controller](https://github.com/NaHSIT/STM32ZET6Project/tree/main/projects/03-button-led-controller)

7月1日，我给前面的双LED项目加上四个板载按键。目标是让三个按键分别控制LED1、LED2和全部熄灭，第四个按键触发五次同步闪烁。

真正写起来才发现，按键不是“读到0就执行”这么简单。机械触点会抖动，按住不放会被主循环重复识别，长时间闪烁还可能吞掉新的输入。这个小控制器让我第一次认真处理人机输入。

---

## 1. 硬件组成

| 按键 | 引脚 | 空闲电平 | 按下电平 |
|------|------|----------|----------|
| S1 | `PE4` | 高 | 低 |
| S2 | `PE3` | 高 | 低 |
| S3 | `PE2` | 高 | 低 |
| WK_UP | `PA0` | 低 | 高 |

输出仍然是`PB5`和`PE5`两盏LED。三枚普通按键用上拉输入，WK_UP用下拉输入，软件判断必须区分两种有效电平。

---

## 2. 消抖不等于等待松手

第一次写法是在检测到按下后延时10ms，再读一次确认。这能过滤触点抖动，却挡不住“按住不放”：主循环转一圈又会读到同一个键，于是动作连续触发。

我后来增加了`previous_key`，只在`0 -> 键值`的变化发生时执行一次动作：

```c
if (key != 0U && previous_key == 0U) {
    handle_key(key);
}
previous_key = key;
```

这相当于把电平判断变成了按下事件。松手后`previous_key`回到0，下一次按下才会再次触发。

---

## 3. 五次闪烁不能卡住主循环

最早的版本直接写五轮`Delay_ms(500)`。效果能看，但整整五秒里CPU只会等待，其他按键全部失去响应。

我改成每10ms运行一次主循环，用`flash_ticks`累计半周期，用`flash_toggles`记录剩余翻转次数。达到500ms就翻转一次LED，其余时间继续扫描按键。

这是一个很小的状态机：它没有操作系统，也没有复杂调度器，只是把“大块等待”拆成很多短步。后面做串口和多外设联动时，这个思路会反复用到。

---

## 4. 调试时最容易看错的地方

我一度以为S3和WK_UP编号反了，后来发现不是代码顺序，而是四个按键的有效电平不一致。用万用表量一次空闲和按下电压，比盯着程序猜快得多。

还有一次按一下触发两次，是因为我只做了10ms确认，却没有保存上一状态。消抖解决的是触点毛刺，边沿检测解决的是重复触发，两者不是一回事。

---

> 按键项目让我意识到，人按一次按钮，在程序眼里其实是一串持续变化的电平。把电平整理成可靠事件，才算真正写好了输入驱动。
